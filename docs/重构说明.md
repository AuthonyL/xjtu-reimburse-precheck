# 报销预检重构说明

重构分阶段进行，每个阶段都保留可验证的边界。阶段一建立领域类型、稳定标识和报销单身份存储；阶段二拆分规则定义、聚合与收集器。阶段二保留现有判定、消息和界面，将声明式规则的“当前判定口径”改由规则参数生成；阶段三接入生命周期与持久化数据层。

## 设计原则

- **发票为一级对象**：发票本身有身份，分组和文件夹组织材料；后续允许围绕发票管理附件及报销归属。
- **报销单有状态机**：主路径为 `draft → ready → submitted → reimbursed`；退回路径为 `submitted → returned → draft`，并预留 `rejected`、`cancelled` 结束状态。流转保留时间和备注；阶段一只定义数据形状，阶段三执行状态迁移。
- **规则是数据**：逐步将规则定义、适用条件和所需材料组织为可验证的数据，迁移时保留当前判定结果。
- **文件夹是真相源**：材料仍以本机文件夹为准，`_预检/claim.json` 保存报销单身份及后续业务状态。移动整个批次时携带该文件即可保留身份。拒票参考目录只读，不创建报销单。
- **问题有稳定标识**：Finding 标识由规则、发票号或相对文件路径及问题代码派生，附件问题还包含材料类型与分组。标识不依赖级别和消息文案，整体移动批次后保持不变。豁免按 `findingId` 记录理由和时间；阶段三在引擎外应用，仍保留原问题。

## 五个阶段

1. **领域层与稳定标识**：建立 Claim、Finding 和 Requirement 的身份，接入本机存储，合并重复逻辑。
2. **规则引擎数据化**：阈值、必附材料、税目、重复票、劳务标准等规则改为统一的数据定义（范围、聚合周期、条件、要求、级别），少数组合规则保留代码实现但登记在同一目录；用新旧引擎对比测试保证判定不变。
3. **报销单生命周期与登记簿**：接入状态机与流转记录，用发票登记簿替代按目录路径记录的提交历史，支持按理由豁免问题，并整理未识别文件的收件箱数据。
4. **前端骨架**：引入状态层与页面路由，拆分大组件，外观与操作保持不变。
5. **新信息架构**：新增收件箱、发票列表和台账页面，批次页改为报销单表单，总览改为可批量操作的列表。

后续阶段的具体接口与迁移方案在实施前确定；以上是阶段目标，不代表已实现的能力。

## 阶段一落地

`src/core/domain/` 定义 Claim、流转和豁免类型及中文形状校验，并统一生成 Finding 标识；纠错模块的 `problemKey()` 保留原有接口与别名映射。Finding 新增 `id`、排序去重的 `ruleIds` 和可选 `resolution`，原复合 `ruleId` 保留；Requirement 在合并规则后按类型、规则、发票号与分组生成标识。

可写批次构建视图时读取或首次创建 `_预检/claim.json`，通过串行队列和现有 JSON 存储写入。新单初始为 `draft`，以一次 `draft → draft` 记录创建时间。Claim 随 `batch.claim` 传递，当前判定不读取其状态或豁免，渲染端不展示；扫描器继续忽略 `_预检/`。

首次创建 `_预检/` 时保留批次目录原修改时间，避免改变依赖该时间推断的批次日期与排序。当前队列只协调同一进程，多应用实例同时首次创建身份尚未协调。

手填匹配统一为 `findManualEntry()`，严重级计数统一为 `countSeverities()`；未完成组依据 `manual-amount` 代码识别，消息原文及原有分组条件保留。测试只使用合成数据，覆盖标识重复性、整体迁移、Claim 持久化与损坏数据、只读目录及报告计数。

## 阶段二落地

`rules/model.ts` 定义规则类别、范围、有效期字段、适用条件与效果，`buildRules(config)` 登记全部 33 条规则。阈值、关键字、税目、购买方、重复票、拒票和劳务标准使用数据定义；高值分支、委托材料分类、外币折算、行程单匹配及劳务组合判定保留编码实现。有效期仅定义字段，当前不参与筛选。`restrictive` 从 `severity === 'error'` 推导，不添加配置键。

新引擎位于 `rules/engine/`：先预计算销方日、实物、高值、组金额、委托集合、支出分类和材料匹配上下文，再按原有阶段执行。收集器按材料类型与聚合目标合并，保留原因及规则插入顺序；付款槽可覆盖其子集，入库单保持 R1/R11/R9 共用槽。稳定标识和处理办法仍由原公共函数生成。劳务判定不变，仅从 registry 读取开关、级别和 L3 标准表。

`rules/engine.ts` 保留兼容导入路径，生产入口使用 `rules/engine/index.ts`。阶段二保留 legacy 引擎供 parity 测试引用，阶段三固定黄金哈希后移除。982 个合成批次同时比较新旧完整结果、规范化结果、原始顺序、报告合计与未折算条目，并检查输入未被修改。规则映射与验收记录由维护者私有保存。

## 阶段三落地

`domain/transitions.ts` 执行合法迁移，终态为已报销、已拒绝和已取消。`createdAt` 独立保存创建时间，新单没有自流转；旧文件缺少该字段时从首条流转时间读取。退回、拒绝需要备注。Claim 的状态、元数据及豁免共用串行队列，每次写入前读取最新文件。

首次刷新按 `samePath` 将尚未绑定 Claim 的旧提交历史迁移到草稿单，保留原提交时间并给 history 补 `claimId`；非草稿单不被覆盖，settings 不变。`markedAt` 返回最近一次进入 submitted 的时间，包括后来退回草稿的单。提交动作继续写一版本兼容 history；退出提交态（已报销除外）撤销该 Claim 的旧历史，避免重新迁移。

`domain/registry.ts` 与 `main/registry.ts` 管理 userData 下的 `registry.json` 缓存。每次刷新用全部当前批次重建，按 Claim 身份替换目录记录；切换根目录时保留仍有相同 Claim 文件的外部记录。查重使用其他 Claim 的 submitted/reimbursed 发票号，并兼容合并旧 history。缓存可删除后重建；从未重新打开的外部批次需再次扫描才能恢复。

扫描为发票来源计算 sha256；`dupChecksum` 默认 false，启用后检查同内容不同发票号的来源。默认值导出时省略该新键，便于旧版本导入；非默认 true 保留，旧版本不能导入此配置。982 条黄金哈希在判定修改前固定，继续逐例校验规范化 CheckResult；语料保留，legacy 引擎与 parity 测试移除。

豁免在 WorkspaceService 构建报告前按 findingId 应用，规则引擎不读取豁免。问题仍保留，严重级和关联材料计数排除已豁免项，汇总末尾写出规则、概述及理由。批次页增加中文状态、合法动作和理由表单，总览增加状态徽标。

`core/inbox.ts` 从未识别文件和 unnamed 附件派生收件箱，按文件名宽松匹配附件关键词并排序建议。manual.json 的可选 ignored 相对路径排除收件箱与未识别 PDF 提示，解析失败诊断保留。IPC 提供读取、忽略和撤销忽略，分类复用附件确认；本阶段未增加收件箱页面。拒票参考目录不写 Claim。

## 阶段四 a 落地

渲染端引入 Zustand，工作区与启动数据、页面路由、操作状态和布局分别放在 `store/` 的四个切片中；展开状态继续使用现有 Disclosure Context。`useRun()` 统一处理 busy、错误和成功通知，`apply()` 执行返回工作区视图的 IPC 并替换视图，组件不再透传 `run`、`update` 和页面选择回调。`App` 组合 `Shell` 与 `Router`：前者负责窗口框架、启动恢复、事件订阅、拖放和快捷键，后者按页面状态选择现有页面；批次选择和侧栏布局仍通过原 IPC 保存。此阶段保留原有界面结构、样式、文案和操作，组件内部拆分及新信息架构留待后续阶段。

## 阶段四 b 落地

界面按 `sidebar/`、`claim/`、`labor/`、`correction/`、`feedback/` 和 `settings/` 拆成实体组件，子组件接收所展示的实体，`ui.tsx` 集中提供文件链接、计数、状态标签、金额和文字按钮。设置标签、折叠内容及问题行、遮罩对话框与已有长文本提示分别改用 Radix Tabs、Collapsible、Dialog 和 Tooltip；侧栏树保留原键盘导航，消息条保留现有实现。折叠表单继续挂载以保留草稿，纠错对话框通过显式 busy 禁用保留原 fieldset 的操作边界。原 `style.css` 已删除，明暗变量放在 `styles/tokens.css`，reset 与共用状态样式放在 `styles/base.css`，其余使用 CSS Modules，保留原间距、边框与窄窗口规则。渲染端启用生产压缩以控制新增依赖的构建体积，文件行数、选择器迁移和验证记录由维护者私有保存。
