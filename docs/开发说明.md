# 报销预检 · 开发说明（Windows / Mac）

面向修改代码、验证规则或自行打包的西交大用户。只使用 APP 请看 [使用说明](使用说明.md)。安装包在 [GitHub Releases](https://github.com/AuthonyL/xjtu-reimburse-precheck/releases)。

本项目不是学校官方工具，预检结果以课题组和财务处最新要求为准。

## 先想清楚：要不要改代码

大部分调整**不需要改代码**，在 APP 里就能完成：

- 关键字、金额门槛、规则开关和级别：「设置 → 规则」；
- 附件识别关键字、分组关键字、支出内容映射、劳务标准：设置里对应的标签。
- 改完后可以在「设置」里**导出规则文件**发给别人，对方导入即可生效。

只有新增一种检查、或者支持一种新的发票版式时，才需要改代码。

## 1. 准备环境（一次性）

1. 安装 **Node.js 24 LTS（64 位）**：<https://nodejs.org>（国内也可用 <https://npmmirror.com/mirrors/node/>）。装完在 PowerShell 里运行 `node -v`，应显示 `v24.x`。
2. 推荐安装 VS Code 作为编辑器。
3. 国内网络建议设置镜像，否则下载 Electron 会很慢。在 PowerShell 里运行：

```powershell
npm config set registry https://registry.npmmirror.com
[Environment]::SetEnvironmentVariable("ELECTRON_MIRROR", "https://npmmirror.com/mirrors/electron/", "User")
[Environment]::SetEnvironmentVariable("ELECTRON_BUILDER_BINARIES_MIRROR", "https://npmmirror.com/mirrors/electron-builder-binaries/", "User")
```

设置完关掉 PowerShell 再重新打开。

## 2. 安装依赖并运行

在源码目录（有 `package.json` 的那一层）打开 PowerShell：

```powershell
npm ci          # 按 package-lock.json 安装依赖，第一次要几分钟
npm run dev     # 以开发模式启动 APP，改界面代码会自动刷新
```

## 3. 代码在哪里

| 目录                           | 内容                                                      |
| ------------------------------ | --------------------------------------------------------- |
| `src/core/parse/`              | 发票解析：PDF（`pdf.ts`）、XML、OFD、海外收据             |
| `src/core/rules/defaults.json` | 所有规则的默认值：关键字、门槛、劳务标准等                |
| `src/core/rules/catalog.ts`    | 规则目录：编号、名称、原文、判定口径；设置页按它自动生成  |
| `src/core/rules/engine.ts`     | 规则判定逻辑                                              |
| `src/core/labor/`              | 劳务费：情况说明解析、标准查表、检查                      |
| `src/core/export/`             | 导出入库登记清单、高值材料明细、汇总                      |
| `src/main/`                    | Electron 主进程：读写文件、中行牌价窗口、放入文件、反馈包 |
| `src/renderer/src/`            | 界面（React）                                             |
| `tests/`                       | 单元测试（只用合成数据）                                  |
| `scripts/`                     | 打包、界面冒烟测试（e2e）、导入反馈包等脚本               |

**改默认规则**：改 `defaults.json`；如果新增了配置项，也要在 `catalog.ts` 里登记，否则单测会提示「有配置项界面上改不到」。

## 4. 改完之后检查

```powershell
npm run format      # 统一代码格式
npm run format:check # 检查格式（CI 不会自动修改）
npm run typecheck   # 类型检查
npm test            # 单元测试，含公开内容守卫
npm run build       # 构建主进程、preload 和渲染进程
npm run e2e         # 界面冒烟测试（会启动 APP 窗口，约 1–2 分钟）
```

全部通过再打包。

## 5. 打包

```powershell
npm run dist:win    # 生成 release\ReimbursePrecheck-<版本号>-win-x64-setup.exe
```

- 版本号在 `package.json` 的 `version` 字段里。改了代码请把版本号加一，例如 `0.1.0` → `0.1.1`，方便区分。
- Mac 安装包（`npm run dist:mac`）只能在 Mac 上打。

## 6. 把改动发回来

为了避免每人手里的版本越改越不一样，改完请把改动发回维护者，由维护者合并进主版本后统一发新安装包：

- 有 Git 的话，发 `git diff` 或提交记录；
- 没有 Git 的话，把改过的文件连同目录结构打包发回，并说明改了什么、为什么改。

遇到解析不了的发票，用 APP 里的「设置 → 反馈 → 导出反馈包」发给维护者，比改代码更快。

## 维护者

### 本地私有验收和课题组规则

公开仓库不含真实资料和私有验收脚本。本机维护者若持有 `private/acceptance.ts`，运行：

```sh
npx tsx private/acceptance.ts <发票根目录>
```

脚本只读源目录，导出在系统临时目录；不要把真实票据或运行记录提交进仓库。`private/`、构建缓存、安装包和截图测试产物均已忽略。旧计划和验收记录位于本机 `private/docs/`。

默认高值材料理由是通用模板。需要课题组私有版本时，自己创建 `private/lab-reasons.json`：

```json
{ "highValueReasons": ["本课题组确认过的理由文本"] }
```

运行 `npm run export-lab-rules`（或 `npx tsx scripts/export-lab-rules.ts`），生成 `private/课题组规则.json`。这是完整 APP 设置格式，可在“设置 → 导入规则 JSON”直接导入；导出时经过同一校验函数，不把私有输入写进公开脚本。

### 导入反馈包

```sh
npm run import-feedback -- <反馈包.zip>
# 如需写到另外的审阅目录：
npm run import-feedback -- <反馈包.zip> --out <目录>
```

导入器校验 ZIP 结构和路径，不覆盖已存在文件。它生成 `tests/fixtures/feedback/` 的诊断 fixture、`tests/feedback/` 中默认 `it.skip` 的回归测试骨架，以及 `private/docs/feedback/` 的维护报告（规则、设置差异、拒票原因和解析清单）。报告不公开；反馈原件不会自动复制到公开源码。

公开提交前仍需人工检查 fixture：脱敏并不保证没有个人信息。优先将问题改写为合成数据，填上期望断言后再启用回归测试。不要直接提交收到的 ZIP 或原发票。

### 合成截图

```sh
npm run screenshots
```

需有图形桌面的机器。脚本与 e2e 共用合成 XML、图片和 Word 生成代码，在系统临时目录的隔离工作区下创建“示例/发票”，独立 userData；窗口内容为 1440×900，强制浅色，隐藏绝对路径行，输出 `docs/images/` 的四张 PNG。不会打开或修改真实资料。完成后清理临时目录，公开截图前再人工检查。

## GitHub Actions 与发布

`ci.yml` 在 push / pull_request 时触发：Windows、macOS、Ubuntu 上执行 Node 24 的安装、格式、类型、单测与构建；Windows / macOS 另跑 Electron e2e。无论 e2e 成败都上传 `test-results/`（保存 14 天）。`.npmrc` 的 `cache=.npm-cache` 是项目本地 npm 缓存；setup-node 通过 `npm config get cache` 使用同一目录，锁文件是缓存键来源，日志会打印实际路径。

发布步骤：

1. 在 `package.json` 和锁文件中确认版本，先让 CI 通过；检查公开内容和合成截图。
2. 维护者创建与版本一致的 `v<版本号>` 标签并推送。`release.yml` 只在版本标签触发；本地脚本不自动发布。
3. 两个打包 job 都先运行格式、类型和单测（含公开内容守卫），任一失败就不上传安装包、也不发布。Windows 托管机器运行 `dist:win`、`verify:packaged`、`e2e:packaged`；ARM macOS 托管机器运行 `dist:mac`（arm64 和 x64 两个 DMG），验证两包资源并运行 arm64 的打包 e2e。主 exe 用纯 JS 改图标/版本，不依赖 wine；Mac 使用 ad-hoc 签名，不做公证。
4. 两个 job 都成功后才创建 GitHub Release，附三个安装包和 `SHA256SUMS.txt`：`v1.2.3` 这样的标签发布为正式版（Latest），带后缀的标签（如 `v1.2.3-beta.1`）发布为预发布。想先给少数人试用时，用带后缀的标签；人工验证安装、系统拦截、Intel Mac 启动以及中行真实页面后，再打正式标签。

本地命令：`npm run dist:win`、`npm run dist:mac`，macOS 上也可 `npm run dist`。产物在 `release/`。Mac DMG 只能在 macOS 生成。

```sh
npm run verify:packaged -- release/win-unpacked
npm run e2e:packaged -- --executable "release/win-unpacked/报销预检.exe"
# macOS arm64：
npm run verify:packaged -- "release/mac-arm64/报销预检.app"
npm run e2e:packaged -- --executable "release/mac-arm64/报销预检.app/Contents/MacOS/报销预检"
```

打包验证检查图标、版本、许可文本、语言包、PDF.js 的 cMap / 字体 / worker / wasm，并隔离加载产物中的 core 解析中文 PDF、导出 Excel 和 Word。GUI e2e 另覆盖界面流程。真实安装、SmartScreen、Gatekeeper 和 Intel 实机运行不由这些测试替代。

## 已知情况

首次跨平台 Actions 结果需要维护者观察。本地通过并不代表托管 Windows GUI 已通过；请以对应运行日志为准。Electron 下载、托管图形会话、文件锁和未签名应用可能导致环境相关失败，失败产物和诊断信息会保留。测试和截图使用合成数据，不依赖真实目录或私有脚本。
